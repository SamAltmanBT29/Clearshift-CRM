### 2.1 Mutation API & Idempotency Protocol (CRM2-03)

- **Atomic Target Mutation & Receipt Persistence**: All migration import writes carry `batch_id`, `source_row` and stable `Idempotency-Key` (header or payload). Target mutation and import receipt share one transaction boundary.
- **Idempotency Replay**: Repeated import requests with the exact same `Idempotency-Key` and identical payload return the original receipt and target ID (`200 OK`) without a second mutation.
- **Idempotency Conflict**: If an `Idempotency-Key` is reused with a different payload digest, the server returns `409 Conflict` (`IDEMPOTENCY_KEY_REUSED`).
- **Protected System Fields**: For user edits (`PATCH /deals/:id`, `PATCH /quotes/:id`), system-maintained fields (`id`, `created_at`, `updated_at`, `is_orphan`, `stage_id`, `deal_id`) are never accepted as authoritative from the browser.
- **Privacy & Safety Guarantees**: Unexpected failures return a stable `correlation_id` and do not leak SQL, stack traces, secrets or raw rows.

## 3. Deal Stage Transitions & Pipeline State Machine (CRM2-06)

The sales pipeline follows a strict directed transition graph:
- **Forward Progression**: `New` -> `Qualified` -> `Proposal` -> `Negotiation` -> `Won`
- **Loss Progression**: Any active stage (`New`, `Qualified`, `Proposal`, `Negotiation`) can transition directly to `Lost`.
- **Idempotency**: Same-stage updates (`current === next`) are permitted.
- **Terminal Stages**:
  - `Won` (`is_won = true`): Closed-Won terminal state. Outgoing transitions: `[]`
  - `Lost` (`is_won = false`): Closed-Lost terminal state. Outgoing transitions: `[]`
- **Forbidden Transitions**: Backward transitions (e.g. `Qualified` -> `New`), skip transitions (e.g. `New` -> `Won`), or transitions originating from terminal stages (`Won` or `Lost`) are strictly rejected before commit with HTTP 422 Unprocessable Entity (`INVALID_DEAL_STAGE_TRANSITION`).

### Transition Matrix

| Current Stage | Allowed Next Stages | Terminal? | Rejection Code on Illegal Transition |
|---|---|---|---|
| `New` | `Qualified`, `Lost` | No | `INVALID_DEAL_STAGE_TRANSITION` (422) |
| `Qualified` | `Proposal`, `Lost` | No | `INVALID_DEAL_STAGE_TRANSITION` (422) |
| `Proposal` | `Negotiation`, `Lost` | No | `INVALID_DEAL_STAGE_TRANSITION` (422) |
| `Negotiation` | `Won`, `Lost` | No | `INVALID_DEAL_STAGE_TRANSITION` (422) |
| `Won` | `[]` | Yes | `INVALID_DEAL_STAGE_TRANSITION` (422) |
| `Lost` | `[]` | Yes | `INVALID_DEAL_STAGE_TRANSITION` (422) |

## 4. Referential Integrity & Validation Rules

1. **CRM-1 Contact Link (`contact_id`)**:
   - Optional / nullable.
   - When null or undefined: Represents an orphan deal. The read API returns `is_orphan: true`, and the UI renders a visible warning badge. An orphan deal is never silently dropped or hidden.
   - When provided (UUID): Resolved via CRM-1's public `ReferenceResolver` or API (`/api/v1/crm-contacts/contacts/{id}`). If the contact ID does not exist, the write operation is aborted before mutation with HTTP 422 Unprocessable Entity (`REFERENCE_NOT_FOUND`, field: `contact_id`).
   - No direct SQL foreign keys or cross-schema writes to `crm1` tables are permitted.
2. **Deal Reference on Quotes (`deal_id`)**:
   - Mandatory foreign key to `crm2.crm2_deals.id`.
   - Verified before commit. Non-existent deal references fail with HTTP 422 Unprocessable Entity (`REFERENCE_NOT_FOUND`, field: `deal_id`).
3. **Quote Number Uniqueness (`quote_number`)**:
   - Unique human-readable quote identifier.
   - Duplicate quote numbers are rejected with HTTP 409 Conflict (`DUPLICATE_RECORD`, field: `quote_number`).

## 6. UI Screens Catalog & Navigation Architecture (CRM2-05)

Every V1 screen is fully integrated and preserves list context navigation:

1. **`DealsListPage` (`/crm-2/deals`)**:
   - Table of sales deals with server-side pagination, search by name/contact, and stage filtering.
   - Distinct badges for pipeline stages and visible warning pill for orphan deals (`is_orphan = true`).
   - Actions: `+ New Deal` (navigates to create form), `View` (navigates to detail view), `Quotes` (opens deal detail quotes).

2. **`DealDetailPage` (`/crm-2/deals/:id`)**:
   - Comprehensive detail view displaying all opportunity attributes.
   - Header with stage pill, orphan badge, and action buttons (`Edit Deal`, `Refresh`, `← Back to Deals`).
   - Overview cards: Value & Stage, Contact Reference (prominent warning for orphan deals), Audit Metadata (read-only IDs and timestamps).
   - Linked Quotes Sub-Table: Lists all quotes attached to this deal, displays server-computed total quote amount, and provides `+ Add Quote` button.

3. **`DealFormPage` (`/crm-2/deals/new` and `/crm-2/deals/:id/edit`)**:
   - Create or edit deal opportunity using `DealForm`.
   - Field-level validation according to OpenAPI contract.
   - Visual orphan deal notice when contact ID is omitted.
   - Read-only system metadata panel when in edit mode.
   - Discard confirmation modal if dirty changes exist.
   - Preserves user input values without loss on server validation errors.

4. **`QuoteFormPage` (`/crm-2/quotes/new` and `/crm-2/quotes/:id/edit`)**:
   - Create or edit commercial quote linked to parent deal using `QuoteForm`.
   - Read-only deal context (parent deal name and UUID).
   - Validates quote number uniqueness, issuance date, decimal amount, and currency.
   - Cancel confirmation if form is dirty.

### 9.2 Bounded Paging & Determinism Constraints

- **Hard Cap at 100**: Requests with `pageSize > 100` or `limit > 100` are strictly rejected with `400 Bad Request` and error code `INVALID_QUERY`.
- **Positive Page Numbers**: Requests with `page <= 0` are rejected with `400 Bad Request`.
- **Deterministic Sort**: Records are deterministically ordered by `created_at desc`, breaking ties by `id asc`. Consecutive pages (`page=1&pageSize=15` and `page=2&pageSize=15`) yield strictly non-overlapping records.
- **SQL Parameterization & Query Safety**: Query parameters are validated strictly with Zod schemas; unknown query parameters are safely stripped without altering database queries or SQL generation.
- **Error Envelope**: All error responses return standard error envelope with `code`, `message`, `details`, and `correlation_id` per PLT-04.

## 11. Chunked Batch Ingestion & Partial-Load Stop Behavior (CRM2-13)

### 11.1 Chunked Processing (500 Rows)
All load operations slice large input datasets into sequential chunks of 500 records (`CRM2_DEFAULT_CHUNK_SIZE = 500`). This bounds database transaction sizes, memory allocation, and lock retention times.

### 11.2 Idempotent Retry with Exponential Backoff
Transient worker or network failures trigger bounded exponential backoff retries:
$$\text{delay} = \text{baseBackoffMs} \times 2^{\text{attempt}}$$
* **Maximum Retries:** Default 3 attempts (`CRM2_DEFAULT_MAX_RETRIES = 3`).
* **Idempotency Protection:** The unique `idempotencyKey` passed per source row is strictly preserved across all retry attempts and never mutated.

### 11.3 10% Partial-Load Stop Policy (`STOPPED_EXCESSIVE_FAILURES`)
To prevent cascading data corruption or runaway failure cascades:
$$\text{failureRate} = \frac{\text{cumulativeFailedRows}}{\text{cumulativeAttemptedRows}}$$
* When `cumulativeAttemptedRows >= 50` and `failureRate > 0.10` (10%):
  1. Batch execution ceases immediately.
  2. Batch status transitions to `STOPPED_EXCESSIVE_FAILURES`.
  3. **Durability Guarantee:** Already committed rows and durable receipts are preserved.
  4. **No Destructive Rollback:** V2 compensating rollback sagas are explicitly out-of-scope; committed data remains intact.
